## ۱. نتیجهٔ یک‌خطی

**بله، کاملاً امکان‌پذیر است و ریسک پایینی دارد.** دی‌ان‌اس و گواهی SSL همین حالا آماده‌اند،
فایل `docker-compose.yml` پروژه از قبل برای چند-نمونه‌ای‌بودن پارامتری نوشته شده، و منابع سرور
(۱۶ گیگ رم، ۸ هسته، ۶۵ گیگ دیسک آزاد) برای یک استک کامل دوم کافی است.
تنها شکاف واقعی: **سازوکار «به‌روزرسانی خودکار» که در README ادعا شده، روی سرور وجود ندارد**
(نه اسکریپت `ci-poller.sh` هست، نه کرون، نه workflow در مخزن فعلی) و باید برای نسخهٔ جدید ساخته شود.
همچنین **کاربر `samim` دسترسی sudo بدون رمز ندارد**؛ تغییرات nginx و گواهی نیاز به حساب root دارد.

## ۳. چیزهایی که از قبل آماده‌اند (کار ما را کم می‌کنند)

1. **دی‌ان‌اس:** `hr.vidara-meeting.ir` همین حالا به `212.80.18.20` resolve می‌شود (بررسی شد).
2. **گواهی TLS:** گواهی موجود، wildcard برای `*.vidara-meeting.ir` است ⇒ **نیازی به صدور گواهی جدید
   و challenge نیست**؛ فقط باید همان `fullchain.pem`/`privkey.pem` در پوشهٔ `deploy/nginx/certs`
   نسخهٔ دوم کپی شود.
3. **پروکسی داخلی پروژه با دامنهٔ پارامتری:** قالب‌های `deploy/nginx/templates/*.template` با
   `envsubst` از `${APP_DOMAIN}`/`${STORAGE_DOMAIN}` ساخته می‌شوند و گواهی از `certs/` خوانده
   می‌شود ⇒ **هیچ تغییری در کد لازم نیست**؛ فقط `.env` نسخهٔ دوم مقادیر خودش را می‌دهد.
4. **جدا‌سازی کامل با نام پوشه:** نام پروژهٔ compose از نام پوشه می‌آید. پوشهٔ فعلی
   `/home/samim/vidara-meetings` ⇒ پروژهٔ `vidara-meetings`. پوشهٔ دوم مثلاً
   `/home/samim/hr-meetings` ⇒ پروژهٔ `hr-meetings` با **شبکه، ولوم، دیتابیس، MinIO و کانتینرهای
   کاملاً جدا**. هیچ تداخل نامی یا داده‌ای رخ نمی‌دهد.
5. **پورت‌های آزاد و بررسی‌شده:** `7081` و `7444` آزادند (پیشنهاد: `APP_PORT=7081` و
   `STORAGE_HOST_PORT=7444` برای نسخهٔ دوم).
6. **آپلود نسخهٔ دوم بدون شبکهٔ بین‌المللی:** بیلد آفلاین است (wheels در `.wheels/` و ffmpeg باندل‌شده)
   ⇒ سرور فیلترشده مشکلی ندارد. فقط دو ایمیج باید یک‌بار ساخته شوند (۵ تا ۱۵ دقیقه).
7. **رفع اشکال دامنه در کد:** در همین بررسی، دامنهٔ اشتباه `vidara.media` (که در `sitemap.xml` و
   `robots.txt` تولید می‌شد) اصلاح شد و به متغیر `VITE_SITE_URL` منتقل شد تا **هر استقرار دامنهٔ
   خودش را در زمان بیلد اعلام کند** — برای نسخهٔ HR مقدار `https://hr.vidara-meeting.ir` تنظیم می‌شود.
   (تست شد: بیلد با این متغیر، sitemap و robots درست تولید می‌کند.)

## ۵. طرح پیشنهادی استقرار (اجرایی، بدون اجرا)

```
مسیر نسخهٔ دوم: /home/samim/hr-meetings          (پروژهٔ compose: hr-meetings)
├── app/                     ← کلون مخزن ebkh2010/HRmeeting (با .git برای pull)
└── deploy/
    ├── .env                 ← تنظیمات اختصاصی (پورت/دامنه/کلیدهای تازه)
    └── nginx/certs/         ← کپی wildcard موجود: fullchain.pem + privkey.pem
```

**مقادیر کلیدی `.env` نسخهٔ دوم:**

| متغیر | مقدار | دلیل |
|---|---|---|
| `APP_DOMAIN` | `hr.vidara-meeting.ir` | دامنهٔ درخواستی |
| `STORAGE_DOMAIN` | `hr.vidara-meeting.ir` | مثل نسخهٔ فعلی، فایل‌ها روی همان دامنه با پورت جدا |
| `APP_PORT` | `7081` | آزاد و بررسی‌شده؛ ۷۰۸۰ در اختیار نسخهٔ فعلی |
| `STORAGE_HOST_PORT` | `7444` | آزاد و بررسی‌شده؛ ۷۴۴۳ در اختیار نسخهٔ فعلی |
| `STORAGE_PORT` | `8443` | داخل کانتینر، بدون تداخل |
| `APP_PUBLIC_URL` | `https://hr.vidara-meeting.ir` | برای لینک‌های ایمیل/ICS |
| `STORAGE_PUBLIC_URL` | `https://hr.vidara-meeting.ir:7444` | مثل الگوی فعلی (`:8443` در نسخهٔ اول) |
| `POSTGRES_DB/USER/PASSWORD` | مقادیر تازه و تصادفی | **هیچ‌کدام از اسرار نسخهٔ اول کپی نشود** |
| `JWT_SECRET_KEY` | مقدار تصادفی تازه | جدا بودن نشست‌ها بین دو نسخه |
| `MINIO_ROOT_*` / `OSS_API_KEY` | تصادفی تازه | جدا بودن استوریج |
| `VITE_SITE_URL` | `https://hr.vidara-meeting.ir` | تا sitemap/robots این نسخه به دامنهٔ خودش اشاره کند |
| `DEFAULT_DEEPSEEK_API_KEY` / `DEFAULT_HARF_*` | کلیدهای AI | فعال‌سازی ماژول‌های هوشمند |

**ترتیب اجرا (پس از تأیید و با دسترسی لازم):**

1. کلون مخزن HRmeeting در `/home/samim/hr-meetings` (کاربر `samim`).
2. ساخت `.env` اختصاصی با پورت‌ها و دامنهٔ بالا و **اسرار تصادفی تازه** (اسکریپت
   `deploy/scripts/init-env.sh` همین کار را می‌کند).
3. کپی `fullchain.pem` و `privkey.pem` گواهی wildcard به `deploy/nginx/certs/` *(نیازمند root)*.
4. `docker compose up -d --build` در پوشهٔ `deploy` (بیلد آفلاین؛ ۵ تا ۱۵ دقیقه).
5. افزودن بلوک لبه به nginx میزبان + `nginx -t && systemctl reload nginx` *(نیازمند root)*.
6. راه‌اندازی سازوکار به‌روزرسانی (poller + کرون کاربر `samim`، بدون نیاز به root).
7. تأیید پایانی: `https://hr.vidara-meeting.ir/health` و بارگذاری یک فایل نمونه.

**معیار پذیرش:**
- نسخهٔ فعلی `https://vidara-meeting.ir` بدون هیچ اختلالی به کار خود ادامه دهد (پورت‌ها و کانتینرها جدا).
- نسخهٔ HR روی `https://hr.vidara-meeting.ir` بالا بیاید، با گواهی معتبر و بدون هشدار مرورگر.
- دو سامانه داده‌های کاملاً جدا داشته باشند (دیتابیس، MinIO، نشست کاربران).
- یک push به `HRmeeting/main` ظرف ≤ ۲ دقیقه روی سرور اعمال شود.

## ۶. تصمیم‌های لازم از طرف شما

1. **دسترسی root:** رمز sudo کاربر `samim` یا رمز root را می‌دهید تا مراحل ۳ و ۵ (گواهی و nginx) را انجام دهم؟ (بقیهٔ کارها با `samim` انجام می‌شود.)
2. **سازوکار آپدیت:** poller روی سرور (پیشنهاد من، پایدار و بدون وابستگی به اینترنت بین‌المللی) یا GitHub Actions؟
3. **مسیر:** `/home/samim/hr-meetings` مناسب است یا مسیر دیگری می‌خواهید؟
4. **پورت‌ها:** `7081` و `7444` تأیید می‌شود؟
5. **کلیدهای AI:** کلید DeepSeek و حساب «حرف» تازه ساخته شود یا از همان‌های نسخهٔ فعلی استفاده شود؟
6. **دامنهٔ فایل‌ها:** مثل نسخهٔ فعلی روی همان دامنه با پورت (`:7444`) یا زیردامنهٔ جدا
   (`storage.hr.vidara-meeting.ir`)؟ (زیردامنهٔ جدید به گواهی و DNS تازه نیاز دارد؛ پورت ساده‌تر است.)
7. **رونوشت داده:** آیا داده‌ای از سامانهٔ فعلی (مثلاً کاربران سازمان) باید به نسخهٔ HR منتقل شود یا کاملاً از صفر شروع می‌شود؟
