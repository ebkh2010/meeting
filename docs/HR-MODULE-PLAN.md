## ۲. تحلیل بازاستفاده: چه چیزی هست و چه چیزی نیست

### ۲٫۱ قابل بازاستفاده بدون تغییر
- **پارادایم کار پس‌زمینه:** ثبت رکورد در `jobs` → `asyncio.create_task(_run_job(job_id))` → polling از فرانت. نوع کار جدید فقط یک `elif` در تابع اجرا و یک ثابت `JOB_*` می‌خواهد.
- **الگوی آپلود:** `POST /upload-url` (presigned PUT روی MinIO) → آپلود مستقیم مرورگر → `POST /recordings` برای ثبت متادیتا. سقف حجم از تنظیمات سازمان خوانده می‌شود (`services/upload_limits.py`).
- **اعتبارسنجی فایل:** PDF/DOCX/تصویر همین حالا در `ALLOWED_ATTACHMENT_TYPES` فرانت و `files.ALLOWED_ATTACHMENT_TYPES` بک‌اند پذیرفته می‌شود؛ پس **رزومه بدون تغییر allow-list آپلود می‌شود.**
- **مدل LLM:** `openai_chat` در `services/ai_providers.py:782` با `response_format={"type":"json_object"}` و `temperature=0.2` — دقیقاً همان چیزی که امتیازدهی ساختاریافته لازم دارد.
- **زمان‌بندی:** جدول `meetings` (شامل `starts_at`, `duration_minutes`, `location`, `online_url`) + `participants` + دعوت‌نامه + ICS + اعلان.

### ۲٫۲ شکاف‌های واقعی (کار جدید)
1. **مدل دادهٔ دامنهٔ HR** — هیچ جدول کاندید/شاخص/ارزیابی وجود ندارد (جست‌وجوی کل مخزن برای `candidate|resume|interview|استخدام|رزومه|مصاحبه` هیچ نتیجهٔ دامنه‌ای نداد).
2. **استخراج متن از رزومه** — `PyMuPDF` موجود است ولی هیچ سرویس پارس رزومه/نرمال‌سازی متن پی‌دی‌اف فارسی نوشته نشده.
3. **پرامپت و قرارداد JSON امتیازدهی** — پرامپت فعلی فقط «صورت‌جلسه» است.
4. **نقش سازمانی HR** — نقش‌ها فقط `org_admin` / `secretary` / `member` هستند (`services/mgmt_core.py:53`). «مدیر استخدام» و «مصاحبه‌گر» باید اضافه شوند یا HR به `org_admin` محدود شود (تصمیم در بخش ۱۱).
5. **OCR** — اگر رزومه اسکن‌شده (تصویری) بیاید، PyMuPDF متن ندارد. هیچ موتور OCR در `.wheels/` نیست ⇒ یا باید wheel آفلاین اضافه شود یا در UI پیام «رزومهٔ اسکن‌شده پشتیبانی نمی‌شود» بیاید (تصمیم در بخش ۱۱).
6. **امتیازدهی گروهی/دسته‌ای (batch)** — الگوی فعلی «یک کار برای یک جلسه» است؛ رتبه‌بندی ۱۰۰ رزومه نیاز به کار دسته‌ای + هم‌زمانی کنترل‌شده + نمایش پیشرفت تجمیعی دارد.
7. **مقایسه و نمودار** — `components/ui/chart.tsx` موجود است ولی هیچ صفحهٔ مقایسهٔ کاندیدها وجود ندارد.
8. **حذف/نگهداری دادهٔ حساس** — `services/media_retention.py` برای مدیای جلسه هست، ولی رزومه/ارزیابی (دادهٔ شخصی) سیاست نگهداری اختصاصی لازم دارد.

### ۲٫۳ قواعد سختِ پروژه که هر پیاده‌سازی باید رعایت کند
| قاعده | منبع در کد |
|---|---|
| هر جدول دامنه `organization_id` دارد و هر کوئری با `get_owned`/`list_owned` محدود می‌شود | `services/mgmt_core.py:228` |
| هیچ کلید API خامی به فرانت نمی‌رود؛ فقط نمای ماسک‌شده | `routers/ai_settings.py` |
| هر عملیات مهم در `audit_logs` ثبت می‌شود | `services/mgmt_core.py:267` |
| جدول جدید = کلاس در `models/` (بارگذاری خودکار از طریق import شدن در روتر + `create_all`) | `core/database.py:239`، `main.py:179` |
| ستون جدید روی جدول موجود = مهاجرت دستی idempotent (نه Alembic اجباری) | `services/database.py` (`ensure_*_columns`) |
| هیچ وابستگی pip تازه بدون wheel آفلاین در `app/backend/.wheels/` | `app/backend/Dockerfile` |
| متن‌ها و پیام‌های خطا فارسی و روشن؛ JSON ساختاریافته از LLM با ترمیم | `services/ai_gateway.py:368` |
| هیچ تاریخ/مهلت/عدد از خودِ مدل ساخته نشود؛ فقط از متن | `_MINUTES_SYSTEM_PROMPT`، `services/ai_gateway.py:262` |

├──────────────────────────────────────────────────────────────────────────────────────────┤

│ ronویسی «حرف»/پلتفرم (موجود)     اعلان ایمیل/پیامک (موجود)      دعوت‌نامه/ICS (موجود)     │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

**تصمیم کلیدی ۱ — مصاحبه یک «جلسه» است یا موجودیت جدید؟**
پیشنهاد: موجودیت جدید `Hr_interviews` که یک `meeting_id` دارد. بدین ترتیب زمان‌بندی،
دعوت‌نامه، ICS، حضور و غیاب و اعلان‌ها از ماژول جلسات قرض گرفته می‌شود، ولی اتاق مصاحبه،
مدیا و ارزیابی در دامنهٔ HR می‌مانند (و در فهرست جلسات عادی سازمان شلوغی ایجاد نمی‌کنند).

**تصمیم کلیدی ۲ — ارزیابی یک جدولِ چندریختی است.**
یک جدول `Hr_evaluations` با `kind = resume | interview` و ستون `scores_json`؛ به‌جای دو جدول موازی.
دلیل: صفحهٔ پروفایل کاندید باید هر دو را در یک تایم‌لاین نشان دهد و مقایسهٔ «امتیاز رزومه در برابر
امتیاز مصاحبه» فقط با یک شکل داده ساده می‌شود.

**تصمیم کلیدی ۳ — امتیاز نهایی همیشه وزن‌دار و سمت سرور محاسبه می‌شود.**
مدل زبانی فقط «امتیاز هر شاخص + شاهد متنی + توصیف» می‌دهد. جمع وزن‌دار، رتبه و آستانه‌ها در
`services/hr_scoring.py` با Python محاسبه می‌شود. دلیل: تکرارپذیری، امکان بازمحاسبه پس از تغییر
وزن‌ها، و جلوگیری از خطای حساب مدل.

## ۶. پایپ‌لاین‌های هوش مصنوعی

### ۶٫۱ پایپ‌لاین ۱ — رزومه → دادهٔ ساختاریافته → امتیاز

```
آپلود → استخراج متن (PyMuPDF/python-docx) → نرمال‌سازی فارسی (fa_normalize موجود)
   → [کار hr_resume_extract]  فراخوان ۱: استخراج JSON
   → [کار hr_resume_score]    فراخوان ۲: امتیاز هر شاخص + شاهد
   → محاسبهٔ جمع وزن‌دار در Python → رتبه → برچسب match_label → رویداد + اعلان
```

**قواعد پرامپت (باید در پیاده‌سازی رعایت شود):**
1. خروجی فقط JSON، بدون بلوک کد، با اسکیمای صریح و شماره‌گذاری شاخص‌ها (همان الگوی `_extract_json_block`).
2. **ممنوعیت ساخت اطلاعات:** اگر سال تجربه، مدرک یا مهارتی در متن نیست ⇒ `null`/`""` — «حدس نزن». (همان قانون سختِ صورت‌جلسه.)
3. **هر امتیاز باید شاهد داشته باشد:** `evidence` = نقل‌قول کوتاه از رزومه یا `""` اگر شاهدی نیست؛ امتیاز بدون شاهد در UI با نشان هشدار نمایش داده می‌شود.
4. مقیاس ثابت (مثلاً ۰ تا ۱۰) و تعریف هر سطح در `levels_json` به مدل داده می‌شود تا امتیاز بین کاندیدها قابل مقایسه بماند.
5. طول متن: رزومه‌های بلند برش زده می‌شوند (سقف ~۱۴٬۰۰۰ کاراکتر مثل `AtomsMinutesAdapter`) و در صورت نیاز به دو قطعه تقسیم و ادغام می‌شوند.
6. دما پایین (`0.2` موجود) و `json_mode=True` ⇒ همان `response_format={"type":"json_object"}`؛ ولی خروجی باز هم باید با `ai_providers.parse_json_object` پارس شود (مدل‌ها گاهی در بلوک کد می‌پیچند).
7. **روی متن رزومه، «شاهد» را با شماره خط یا نقل‌قول دقیق برگردانید** تا در UI با `HighlightText` برجسته شود.

### ۶٫۲ پایپ‌لاین ۲ — مدیای مصاحبه → رونویسی → ارزیابی

```
آپلود چند فایل (ترتیب دلخواه) → [ffmpeg] جداسازی صدا برای ویدیو → [کار transcribe موجود]
   → رونویسی + گوینده‌ها → تصحیح دستی گوینده‌ها
   → [کار hr_interview_eval]  فراخوان: امتیاز شاخص‌محور + شاهد زمان‌دار + توصیهٔ نهایی
   → محاسبهٔ امتیاز نهایی وزن‌دار → مقایسه با امتیاز رزومه → بازبینی انسانی → قفل
```

**نکات حیاتی:**
- **نقش گوینده‌ها تعیین‌کننده است:** ارزیابی «کیفیت پاسخ کاندید» بدون دانستن اینکه کدام جمله از کاندید است بی‌معناست. خوشبختانه کاتالوگ فعلی `STT_CATALOG` (`services/ai_providers.py:71`) برای «حرف (روشن)» و ElevenLabs ستون `supports_diarization: True` دارد؛ ولی Whisper ندارد. پس اگر سازمانی Whisper را انتخاب کند، تفکیک گوینده ممکن نیست و باید با انتخاب دستی «کدام گوینده کاندید است» حل شود (فیچر F4).
- **رندر زمان‌دار برای LLM باید ساخته شود:** مسیر صورت‌جلسه فقط `full_text` را به مدل می‌دهد و **timestamp نمی‌فرستد**؛ زمان‌ها فقط در `segments_json` هستند. برای ارزیابی مصاحبه باید یک هلپر جدید بنویسید که هر قطعه را به شکل `[mm:ss] گوینده: متن` رندر کند؛ در غیر این صورت ارجاع به لحظهٔ نقل‌قول (فیچر G2) ممکن نیست.
- **مصاحبه‌های بلند:** هیچ برش/تکه‌کردنی در پروژه وجود ندارد و کل فایل در یک درخواست ارسال می‌شود. صدای استخراج‌شده مونو/۱۶kHz/۶۴kbps حدود ۲۸ مگابایت در ساعت است (برای «حرف» مشکلی نیست) ولی Whisper سقف ۲۵ مگابایت دارد ⇒ برای مصاحبهٔ بلند باید با `ffmpeg -f segment` تکه‌کرد و سپس متن‌ها را با آفست زمانی به هم چسباند. این کار در WP6 دیده شده است.
- **قواعد سختِ خروجی:** ممنوعیت ساخت نقل‌قول، الزام شاهد زمان‌دار برای هر امتیاز، و برچسب صریح «خارج از رونویسی» برای هر استنباط.
- **مرز اخلاقی/حقوقی:** در UI و در سند ارزیابی صریح نوشته شود که خروجی AI «کمک‌کننده» است و **تصمیم نهایی انسانی** است؛ ویژگی‌های حساس (سن، جنسیت، قومیت، وضعیت تأهل) نباید در پرامپت ارسال شوند.

from services.ai_providers import parse_json_object, AIGatewayError

HR_SCORING_SYSTEM_PROMPT = "… فقط یک شیء JSON معتبر برگردان …"   # هم‌سبک با _MINUTES_SYSTEM_PROMPT

async def score_resume(db, organization_id, *, resume_text: str, criteria: list[dict], position_title: str) -> dict:
    # ۱) تضمین وجود زنجیرهٔ تأمین‌کننده‌ها (run_chat خودش این کار را نمی‌کند)
    await ai_providers.ensure_defaults(db, organization_id)

    # ۲) تخمین هزینه پیش از فراخوان برای کنترل بودجهٔ کاربر
    est_in  = ai_usage.estimate_minutes_tokens(resume_text, HR_SCORING_SYSTEM_PROMPT, user_prompt)
    est_out = 800
    est_cents = ai_usage.cost_cents_for("deepseek", est_in, est_out)

    # ۳) فراخوان با زنجیرهٔ اولویت سازمان
    text, provider_key, attempts, usage = await ai_providers.run_chat(
        db, organization_id,
        system_prompt=HR_SCORING_SYSTEM_PROMPT,
        user_prompt=build_resume_prompt(resume_text, criteria, position_title),
        json_mode=True,
    )
    # ۴) run_chat هرگز استثنا نمی‌دهد؛ متن خالی = شکست
    if not text:
        raise AIGatewayError("هیچ مدل زبانی فعالی پاسخ نداد. " + ai_providers.format_attempts(attempts))

    payload = parse_json_object(text)          # عمومی و آماده در ai_providers
    return {
        "scores": normalize_scores(payload, criteria),   # نگاشت به شاخص‌های تعریف‌شده + اعتبارسنجی بازه
        "provider": provider_key,
        "attempts": ai_providers.format_attempts(attempts),
        "usage": usage,
        "cost_cents": ai_usage.cost_cents_for(provider_key, usage["tokens_in"], usage["tokens_out"]),
        "est_cents": est_cents,
    }
```

**انواع مصرف جدید:** `KIND_RESUME_SCREEN = "resume_screen"` و `KIND_INTERVIEW_EVAL = "interview_eval"` را
به `KIND_LABELS` در `services/ai_usage.py` اضافه کنید (اگر اضافه نشود، `KIND_LABELS.get(kind, kind)`
خودش kind خام را نشان می‌دهد و چیزی نمی‌شکند). نکته: خلاصه‌های مصرف در پنل پلتفرم فقط بر پایهٔ
`provider` تجمیع می‌شوند، پس `provider` باید همان `provider_key` واقعی بماند.

**برآورد هزینهٔ نمونه (برای UI):** هر رزومه حدود ۳–۶ هزار توکن ورودی و ۱–۲ هزار خروجی ⇒ با نرخ
DeepSeek حدود **۱ تا ۳ سنت** برای هر رزومه (و چون `cost_cents_for` حداقل ۱ سنت برمی‌گرداند، هر
فراخوان دست‌کم ۱ «توکن ویدارا» ثبت می‌کند). ارزیابی هر مصاحبهٔ ۳۰–۶۰ دقیقه‌ای به‌مراتب سنگین‌تر
است (رونویسی ۳۰–۶۰ توکن + متن بلند) و باید در UI پیش از اجرا نمایش داده شود.

### ۷٫۳ استقرار و عملیات
- **بدون وابستگی جدید pip** اگر ممکن است: کد فعلی فقط از `PyMuPDF` (خواندن پی‌دی‌اف) و `python-docx` (خواندن/نوشتن Word) می‌تواند استفاده کند و **هر دو wheel آفلاین در `.wheels/` موجودند** (همراه `lxml` و `pillow`). کتابخانه‌های `pdfplumber`/`pypdf`/`unstructured`/`tesseract` در wheelها **نیستند** ⇒ افزودن آن‌ها روی سرور بدون PyPI ممکن نیست.
- **استخراج متن رزومه نمونهٔ آماده ندارد:** استفادهٔ فعلی `fitz` در `services/aihub.py:525` فقط برای «برش بازهٔ صفحه و ارسال به مدل» است و متن را به رشته تبدیل نمی‌کند؛ پس `page.get_text()` و خواندن پاراگراف/جدول‌های `docx` در سرویس HR باید از صفر نوشته شود (حدود نیم‌روز).
- **`.doc` قدیمی پشتیبانی نمی‌شود** (`python-docx` فقط `.docx` می‌خواند) ⇒ در UI فقط `.pdf` و `.docx` و `.txt` پذیرفته شود با پیام روشن.
- مهاجرت با `create_all` کافی است؛ برای ستون‌های جدید روی جداول موجود، به `ensure_platform_columns()` در `services/database.py` اضافه کنید.
- **حذف سازمان:** همهٔ جدول‌های `Hr_*` به `ORG_DELETION_TABLES` در `routers/app_auth.py` اضافه شوند تا حذف سازمان داده‌ی کاندید را جا نگذارد.
- به‌روزرسانی `docs/architecture.md` و افزودن ADR برای تصمیم‌های «مصاحبه = جلسه»، «جدول ارزیابی واحد»، «امتیاز وزن‌دار سمت سرور»، «سهمیهٔ ظرفیت HR».
- تست‌های `pytest` برای سرویس‌های جدید + تست مرز مستأجر (کاربر سازمان A نباید کاندید سازمان B را ببیند).

### ۹٫۱ مهارت‌هایی که **لازم نیست** (خارج از دامنه)
- آموزش/فاین‌تیون مدل، OCR پیشرفته، تحلیل چهره و لحن از ویدیو، یکپارچگی با ATS خارجی، موتور جست‌وجوی برداری (vector DB) — همه در فاز ۲/۳ و اختیاری.
- Celery/Redis/Kafka: معماری پروژه عمداً بدون آن‌هاست؛ نباید اضافه شود.
- Next.js/GraphQL/پایگاه دادهٔ جدید: پشته ثابت است.

### ۹٫۲ سطح‌بندی مهارت برای واگذاری
| نقش | مهارت‌های لازم | مناسب برای |
|---|---|---|
| **عامل پایه (Base agent)** | S1، S2، S11، S14 | CRUD جدول‌ها، فرم‌ها، فهرست‌ها، صفحات ساده |
| **عامل میانی (Mid agent)** | + S6، S8، S9، S12، S13، S18 | آپلود، مدیا، جدول رتبه، گزارش |
| **عامل ارشد (Senior agent)** | + S3، S4، S5، S7، S10، S15، S17، S22 | پرامپت‌ها، امتیازدهی، ارزیابی مصاحبه، سخت‌سازی |
| **بازبین انسانی (Human reviewer)** | دامنهٔ HR + تصمیم دربارهٔ بخش ۱۱ | تعیین شاخص‌ها، آستانه‌ها، سیاست نگهداری، تأیید نهایی امتیازها |

**توصیهٔ عملی:** WP3 و WP7 (پرامپت و امتیازدهی) را به یک عامل با S3/S4/S22 بسپارید و خروجی را با
«مجموعهٔ طلایی» بسنجید؛ بقیهٔ بسته‌ها با عامل میانی قابل انجام است.

## ۱۰. معیارهای پذیرش و سناریوهای تست

### ۱۰٫۱ سناریوهای سرتاسری
1. **رزومه → رتبه:** آپلود ۱۰ رزومهٔ فارسی (PDF و DOCX مخلوط) در یک موقعیت ⇒ همه تحلیل شوند؛ جدول رتبه با امتیاز هر شاخص، شاهد متنی و برچسب واجد شرایط/مرزی/رد.
2. **تغییر شاخص‌ها:** وزن یک شاخص از ۱۰ به ۳۰ تغییر کند ⇒ رتبه‌ها بازمحاسبه شوند و **هیچ فراخوان LLM جدیدی** ثبت نشود (بررسی در `ai_usage_events`).
3. **مصاحبهٔ ویدیویی:** آپلود ویدیوی ۶۰ دقیقه‌ای ⇒ جداسازی صدا، رونویسی زمان‌دار، تصحیح گویندهٔ کاندید ⇒ ارزیابی با امتیاز هر شاخص + توصیه + شاهد زمان‌دار.
4. **بازبینی انسانی:** مصاحبه‌گر امتیاز یک شاخص را اصلاح کند ⇒ امتیاز نهایی و رتبه به‌روز شود، تغییر در Audit و تایم‌لاین ثبت شود، ارزیابی قفل شود.
5. **مرز مستأجر:** کاربر سازمان B با شناسهٔ کاندید سازمان A ⇒ ۴۰۴؛ در فهرست، هیچ رکورد سازمان A دیده نشود.
6. **دسترسی:** عضو عادی سازمان (نقش `member`) ⇒ ۴۰۳ روی همهٔ مسیرهای HR.
7. **پاک‌سازی:** کاندید با `purge_after` گذشته ⇒ فایل رزومه و مدیا حذف، ولی رکورد و Audit باقی بماند.
8. **موبایل:** کل مسیر روی عرض ۳۲۰px بدون سرریز افقی و با جدول کارتی.
9. **خرابی سرویس AI:** کلید DeepSeek نامعتبر ⇒ پیام فارسی روشن، کار در وضعیت `failed`، هیچ دادهٔ نیمه‌کاره‌ای ذخیره نشود.

### ۱۰٫۲ کیفیت پرامپت (مجموعهٔ طلایی)
- ۲۰ رزومهٔ واقعی فارسی (شامل رزومهٔ دوستونه، جدولی، با فونت‌های عجیب و فایل اسکن‌شده).
- ۵ رونویسی مصاحبهٔ ۱۰–۲۰ دقیقه‌ای با کیفیت‌های متفاوت صدا.
- سنجه‌ها: نرخ JSON معتبر، نرخ امتیاز با شاهد، پایداری امتیاز در دو اجرای متوالی (انحراف ≤ ۰٫۵ در مقیاس ۱۰)، نبود اطلاعات ساختگی (بررسی موردی سال تجربه/مدرک).

## ۱۱. ریسک‌ها و تصمیم‌های باز

### ۱۱٫۱ ریسک‌ها
| ریسک | اثر | کاهش |
|---|---|---|
| توهم مدل در استخراج (مدرک/سابقهٔ ساختگی) | تصمیم استخدامی غلط | شاهد اجباری + ممنوعیت حدس در پرامپت + بازبینی انسانی + نشان «بدون شاهد» در UI |
| سوگیری و پیامد حقوقی | شکایت/بی‌اعتباری | حالت بررسی کور، حذف ویژگی‌های حساس از پرامپت، مستندسازی شاخص‌ها، تصمیم نهایی انسانی |
| رزومهٔ اسکن‌شده/فارسی بدساختار | استخراج ناقص | تشخیص خودکار «متن استخراج نشد» + پیام روشن + (اختیاری) افزودن OCR آفلاین |
| هزینهٔ AI روی حجم بالا | هزینهٔ غیرمنتظره | برآورد پیش از اجرای دسته‌ای + بودجهٔ ماهانهٔ HR + بازمحاسبه بدون LLM |
| فایل صوتی طولانی/چند گوینده | رونویسی ناقص یا برچسب اشتباه | برش با `ffmpeg -f segment` + تصحیح دستی گوینده + امکان ورود متن دستی + محدودکردن انتخاب Whisper برای فایل بلند (سقف ۲۵ مگابایت) |
| رقابت صف HR با صف جلسات روی سقف ظرفیت | کندشدن سامانهٔ اصلی سازمان | شمارندهٔ ظرفیت مستقل HR یا سهمیهٔ اختصاصی (تصمیم باز #۸) |
| قطع سرور وسط پردازش رزومه/مصاحبه | کار نیمه‌کاره (کارها قابل ادامه نیستند) | ذخیرهٔ نتیجه در دیتابیس پیش از تغییر وضعیت + دکمهٔ «تلاش دوباره» + عدم فراخوان دوباره اگر نتیجه هست |
| افشای دادهٔ کاندید | بحران اعتماد | مرز مستأجر، نقش‌محوری، Audit دسترسی، نگهداری محدود، عدم ارسال داده به سرویس غیرقراردادی |
| بزرگ‌شدن `meeting_ai.py` | نگه‌داشت‌پذیری | `_run_job` مستقل در `routers/hr.py` (الگوی `archive.py`) |

### ۱۱٫۲ تصمیم‌های باز (نیاز به پاسخ شما)
1. **نقش‌ها:** «مدیر استخدام» و «مصاحبه‌گر» به‌عنوان نقش سازمانی جدید اضافه شوند، یا فعلاً فقط `org_admin` دسترسی HR داشته باشد؟
2. **رزومهٔ اسکن‌شده:** OCR آفلاین اضافه شود (افزودن wheel به `.wheels/`) یا فعلاً پیام «پشتیبانی نمی‌شود» کافی است؟
3. **ارزیابی ویدیویی (لحن/چهره):** خارج از دامنهٔ فاز ۱ و ۲ بماند؟ (پیشنهاد: بله)
4. **چند مرحله مصاحبه:** چند دور مصاحبه (فنی/HR/مدیر) با شاخص‌های متفاوت برای هر دور لازم است یا یک دور؟
5. **ادغام با جلسات:** مصاحبه در فهرست جلسات عادی سازمان دیده شود یا فقط در بخش HR؟ (پیشنهاد: فقط HR + لینک به جلسه)
6. **مقیاس:** حجم واقعی رزومه در ماه (۱۰، ۱۰۰، ۱۰۰۰؟) — تعیین‌کنندهٔ طراحی صف و UI.
7. **زبان:** فقط فارسی یا رزومه/مصاحبهٔ انگلیسی/دوزبانه هم باید پشتیبانی شود؟
8. **سقف ظرفیت موتور AI:** صف HR با صف جلسات **سهمیهٔ مشترک** داشته باشد (ساده، ولی بار سنگین
   استخدام می‌تواند رونویسی جلسات را بلاک کند) یا **شمارندهٔ مستقل** برای HR با سقف اختصاصی در
   `Hr_settings`؟ (پیشنهاد: مستقل، چون الگوی فعلی `_count_active_jobs` همهٔ کارهای سیستم را
   می‌شمارد و صف HR روی سقف ۳/۱۰ با جلسات رقابت می‌کند.)
9. **مدل اختصاصی ارزیابی:** ارزیابی HR با همان مدل پیش‌فرض سازمان انجام شود یا مدل قوی‌تری
   برای این ماژول pin شود؟ (یادآوری: امکان تعیین مدل هر فراخوان وجود ندارد؛ اگر مدل جدا لازم است،
   ردیف تأمین‌کنندهٔ LLM اختصاصی باید seed شود.)

## ۱۲. نکات امنیتی (فوری، خارج از دامنهٔ فیچر)

- توکن GitHub که در پیام ارسال شد، **در متن گفتگو افشا شده است** و باید همین امروز در GitHub باطل (revoke) و توکن جدید ساخته شود.
- بررسی انجام‌شده نشان داد نسخهٔ محلی در `dockerv23` دقیقاً روی همان کامیت `refs/heads/main` مخزن
  `ebkh2010/meeting` است (`9fa502793730732f5e74975bc94ab19cd93a4bce`).
- **وضعیت انتقال:** کل پروژه (۴۵۹ فایل، شامل بسته‌های آفلاین `.wheels/` و ffmpeg/ffprobe باندل‌شده)
  به مخزن خصوصی `ebkh2010/HRmeeting` منتقل شد و با کلون تازه تأیید شد. شاخهٔ `main` آن مخزن اکنون
  روی کامیت `6b04711` است که همین سند را هم دارد.
- **دسترسی SSH برای مخزن جدید کار نمی‌کند** (`Repository not found`) چون کلید SSH این ماشین به آن
  مخزن/حساب وصل نیست؛ انتقال با توکن HTTPS انجام شد. برای push های بعدی:
  `git push hr main` با توکن HTTPS (ریموت `hr` بدون توکن در `.git/config` تنظیم شده است).
- هیچ توکنی در فایل‌های مخزن ذخیره نشد و نباید بشود (`.gitignore` را رعایت کنید).
- **دو فایل بزرگ هشدار GitHub گرفتند** (`app/backend/bundle/bin/ffmpeg` و `ffprobe`، هرکدام ~۷۶ مگابایت
  بزرگ‌تر از سقف پیشنهادی ۵۰ مگابایت). push موفق شد، ولی اگر مخزن جدید برای توسعهٔ HR جدی است،
  بهتر است این دو باینری به Git LFS منتقل شوند یا از مخزن بیرون بیایند و در استقرار جداگانه تأمین شوند.
